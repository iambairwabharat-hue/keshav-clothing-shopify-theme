Introduction

Everything a partner needs to connect an external application to Miracle Cloud ERP — securely, predictably, and with clear error semantics.

Purpose

This manual provides a complete and comprehensive guide for integrating third-party applications with the Miracle Cloud ERP platform. It details the API structure, the secure OAuth authentication flow, standard data formats, and module-wise integration steps, enabling seamless and error-free data exchange.

API Conventions

These rules apply to every endpoint. They are stated once here and not repeated on each call.

The action Field

ValueMeaningNotes
AAdd — create a new recorduniqueId may be omitted or empty.
EEdit — update an existing recorduniqueId is mandatory and must reference an existing record.

Standard Response Envelope

Write operations return a consistent envelope. Always test IsError before consuming the result.

RESPONSE ENVELOPE — WRITE OPERATIONS
{  "UniqueId":  "string  — ERP-assigned ID of the affected record",  "IsError":   false,  "ErrorCode": "",  "Message":   "Record Added Successfully."}

Linked Vouchers {LinkedVouUniqueId}

Inter-branch vouchers create a counterpart record in the destination branch. When that happens the write response carries an additional LinkedVouUniqueId array — one element per counterpart voucher created. The array is absent on vouchers that do not cross branches.

FieldDescription
UniqueIdUnique ID of the counterpart voucher created in the destination branch.
BranchIdDestination branch uniqueId, as returned by Get Branch List.
RESPONSE ENVELOPE — INTER-BRANCH VOUCHER
{  "UniqueId": "14082026175841b7d9b1",  "LinkedVouUniqueId": [    { "UniqueId": "140820261758416168b1", "BranchId": "0961ebfa63" }  ],  "IsError":   false,  "ErrorCode": "",  "Message":   "Record Updated Successfully."}
Which flows return it
Branch Transfer Issue (WA), Branch Contra (origin = BC), and Branch Journal (origin = BJ). See Sections 8.8 – 8.10.

Request Headers

Two headers cover the whole API. The authentication call is the one exception: it carries no token, and sends its credentials as headers rather than as a body.

HeaderValueApplies ToRequired
AuthorizationBearer {token}All TPA/M2/V1/ endpointsYes
Content-Typeapplication/jsonPOST endpoints only, which carry a request bodyYes
clientId{clientId}CLAuth/Authenticate onlyYes
apiKey{apiKey}CLAuth/Authenticate onlyYes
GET endpoints send no body
The five GET endpoints need Authorization only. There is no request body to describe, so Content-Type is not required.

Base URL & Paths

Request lines in this guide are written as {baseurl}TPA/M2/V1/.... Substitute the base URL from Section 3, which already ends in a slash, so the endpoint path follows without a leading slash.

Two things to get right
Joining a base URL ending in / to a path starting with / produces ...com//TPA/M2/V1/.... It may be tolerated, but some gateways and proxies reject it. Endpoint paths are also written in uppercase: use TPA/M2/V1/, not tpa/M2/V1/.

User Fields {ufddet}

Verify

Account, Product, and Voucher payloads accept an optional ufddet object carrying the user-defined fields configured in Cloud Miracle. Each key is a user-field code; each value must match the data type that field was set up with.

Field Data TypeJSON TypeLengthFormat

Environments & Prerequisites

BASEhttps://tpaapi.miracleclouderp.com/

Enable TPA Integration (one-time setup)

  1. Log in to the Partner Login portal.
  2. Navigate to Setup → Company Setup → Advanced Modules → TPA Options.
  3. Set TPA Integration Required = Yes.
  4. Set TPA Callback Integration Required = Yes only if callback functionality is required.

Generate Credentials

  1. Navigate to Partner Login → Setup → TPA Setup → TPA User Setup.
  2. Generate the TPA Username, Client ID, and API Key.
  3. Set the TPA User Status to active.

Credential Reference

CredentialScope / UniquenessUsed As
TPA UsernamePer TPA userIdentifies the integration account
Client IDUnique per company, per usernameclientId
API KeyUnique per company, per financial year, per branchapiKey
URL KeyOwner-level; appears in the login URL as uKey=XXXXurlKey
Security
Keep the Client ID, API Key, and bearer tokens secret. Treat them like passwords — never embed them in client-side code or commit them to source control.

Callback / Webhook Integration

Cloud Miracle can push real-time notifications to your application whenever a record is added, edited, or deleted — so you no longer need to poll for changes.

15.1 How It Works

When callback integration is enabled, Cloud Miracle sends an HTTP POST to your registered callback URL each time a relevant event occurs. The notification is lightweight: it identifies the event type and the affected record's unique ID. Your application then calls the matching GET endpoint to retrieve the full record.

  1. An event occurs in Cloud Miracle (an account, product, or transaction is added, edited, or deleted).
  2. Cloud Miracle POSTs a JSON notification to your configured callback URL.
  3. Your endpoint verifies the request and responds with HTTP 200.
  4. For add/edit events, your application calls the relevant GET endpoint (GetAccount, GetProduct, or GetVoucher) using the supplied UniqueId to fetch full details.
Design note
Callbacks carry only the event type and the record's UniqueId — not the full record. This keeps notifications small and secure. Always fetch the current record via the GET endpoints rather than relying on cached data.

15.2 Enabling Callbacks

Callback integration is configured entirely from the Partner Login portal — there is no API for registration.

Step 1 — Turn on callback integration

  1. Navigate to Setup → Company Setup → Advanced Modules → TPA Options.
  2. Set TPA Callback Integration Required = Yes.

Step 2 — Register the callback URL

  1. Navigate to Partner Login → Setup → TPA Setup → TPA Callback Setup.
  2. Add or edit a callback entry and provide the fields below.

Callback Setup Fields

The Callback Setup screen also exposes fields for token-based authentication (Static Header, Static Params, Auth URL, Auth API Method, Auth Request Payload, Auth Response Path, Token Expiry Time). These support future authenticated modes and are not required for the current Anonymous mode.

15.5 Verifying the Callback

Because the current Auth Mode is Anonymous, incoming callbacks carry no signature header or bearer token. Verify authenticity from the body instead:

  • Confirm the APIKey matches the API Key issued to your integration.
  • Confirm the ClientId matches your Client ID.
  • Reject the request if either value does not match.
Security best practice
Expose your callback endpoint over HTTPS only, and treat the APIKey as a secret. As an additional safeguard you may restrict inbound traffic to Cloud Miracle's IP range.

15.6 Responding & Retries

Your endpoint must acknowledge every callback promptly.

AspectBehaviour
Success responseReturn HTTP 200. Any other status (or a timeout) marks the callback as failed.
Automatic retriesFailed callbacks are retried automatically up to 20 times.
Retry intervalApproximately 2 minutes between attempts.
TrackingEach attempt updates Retry Count, Last Retry At, and Next Retry At.
Manual retryFailed callbacks can be re-sent manually from the Callback Details screen.
Tip
Acknowledge quickly, then process asynchronously. If you run heavy logic before returning 200, the request may time out and be counted as failed. Return 200 first, then fetch the record and update your system in the background.

15.7 Monitoring Callbacks

Administrators can review delivery status and payloads from the Callback Details report at Admin → Utility → TPA Setup → TPA Callback Details.

The report lists each callback with its Request time, TPA User, Client ID, Event Type, Status, Retry Count, Last Retry At, and Next Retry At. It supports filtering by Status and Type, a date range, and free-text search.

Two actions are available on this screen: View Payload shows the exact JSON that was sent, and Retry Callback re-sends a selected notification on demand.
